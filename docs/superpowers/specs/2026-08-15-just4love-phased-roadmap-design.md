# 遇见爱（just4love）1.0.1 分阶段实现路线图 — 设计文档

- **日期**：2026-08-15
- **状态**：P1 已完成并验收；P2 已完成（实现计划见 `plans/2026-08-19-just4love-p2-meet-browse-quota.md`）；P3 待启动
- **范围**：将「遇见爱」1.0.1 版本功能拆解为 5 个可独立上线的阶段，并定义各阶段边界、数据模型演进与贯穿性约定

## 1. 背景与目标

产品核心价值：高质量、提升相亲效率、保护隐私安全。

当前仓库状态（2026-08-13 骨架已完成）：3 个 tabBar 页（推荐/消息/我的，均为 mock 数据）、`recommend-card` 简单卡片、`getProfile` 示例云函数、完整三层测试基础设施（Jest 单测 / 云函数集成 / miniprogram-automator E2E）。

1.0.1 版本的功能全景远大于骨架，包含六大块：注册登录、角色配额、遇见（筛选+资料卡）、匹配（语音/视频/附近的人/DNA/话题/故事）、我的（资料编辑/认证/设置）、运营（上墙/推荐/交友群）。本设计将其拆为 5 个阶段，**每个阶段结束都是一个可上线、可演示的版本**。

## 2. 已确认的关键决策

| # | 决策 | 结论 |
|---|---|---|
| 1 | 阶段划分原则 | 按用户价值闭环分阶段（方案 A），每阶段可上线可验收 |
| 2 | 供需顺序 | **登录+个人资料先行，浏览后行**（P1/P2 调换过）——团队成员通过产品 UI 注册填资料即为真实数据，无需种子数据脚本；dogfood 资料编辑流程；角色配额规则在浏览上线时一步到位 |
| 3 | 主体资质 | 企业主体——手机号快速验证、婚恋交友类目、位置等能力可用 |
| 4 | 匹配模块 | 降级简化：DNA/标签/话题/故事匹配用问卷+标签数据实现；语音/视频聊天不自建（交换联系方式后用微信）；群聊用交友群二维码代替 |
| 5 | 管理端形态 | P1-P3 用云开发控制台直接操作数据库；P4 做小程序内管理员专属页 |
| 6 | IM 方案 | 不自建 IM：心动互配 → 征求同意交换联系方式 → 微信聊天；消息 tab 只承载系统通知 |

**P1/P2 调换的风险及对策**：调换后 P1 结束时看不到「浏览他人资料」这一核心体验。对策：P1 包含「我的资料卡预览」——用自己的数据渲染完整资料卡组件（即遇见卡片的显示层），显示层在 P1 即被验证。

## 3. 阶段总览与依赖

```
P1 登录+个人资料       P2 遇见：浏览与配额        P3 互动+隐私授权
（用户注册成为嘉宾）→ （列表/筛选/详情/配额） →  （心动/通知/解锁联系方式）
      ↓                     ↓
  自己的资料卡预览      P4 认证+管理能力 → P5 匹配增强（降级版）
```

| 阶段 | 一句话目标 | 结束时可上线形态 |
|---|---|---|
| P1 | 注册登录 + 完整资料编辑 + 自己的卡片预览 | 供给端闭环（用户=嘉宾，团队注册即为真实数据） |
| P2 | 遇见列表 + 筛选 + 详情页 + 角色配额 | 供需闭环（可浏览、可筛选） |
| P3 | 心动互配、征求同意解锁联系方式、系统通知 | 完整互动闭环（导流微信聊天） |
| P4 | 人工认证 + 小程序内管理页 | 可运营 |
| P5 | 恋爱 DNA + 标签/话题/故事匹配（降级版） | 差异化（附近的人为可选项） |

## 4. P1 — 登录与个人资料（供给先行）

**目标**：用户注册后能完善一份完整相亲资料，并预览自己的资料卡。

### 4.1 登录体系
- 微信静默登录：云函数 `getWXContext()` 取 openid，首次自动创建 `users` 文档；**注册仅靠微信静默登录即可完成**
- 手机号绑定：`getPhoneNumber` 按钮（企业主体能力），**可选绑定**（用于联系方式字段预填与账号找回，不绑定不影响注册和资料编辑）
- 登录态存本地缓存，启动时恢复

### 4.2 数据模型（首批集合）
- `users`：openid、手机号、角色（`guest/normal/verified/admin`，字段预置，**配额执行留到 P2**）、嘉宾编号（自动生成，`J0001` 递增）
- `profiles`：与资料卡一一对应的完整字段（基本信息、关于我/希望你、标签、家庭背景、相册、故事、隐私字段）
- 管理员指定方式：云开发控制台手改 `role`（P4 前的约定）

### 4.3 我的 tab — 资料编辑
- **基本资料**：头像（要求真人，云存储上传；P1 不做技术校验，真人把关依赖 P4 人工认证/上墙审核）、嘉宾编号（只读自动生成）、昵称+性别（注册时确定，锁定不可改）、生日→星座（锁定，自动推算）、个性签名
- **相亲信息**：关于我、希望你、恋爱目标（4 选项：短期内想结婚 / 认真谈场恋爱如果合适可以考虑结婚 / 先认真谈场恋爱再说 / 没考虑清楚）、情感状态、身高/学历/职业/现居地/家乡/学校、家庭背景（12 项多选：独生子女、有兄弟姐妹、知识分子家庭、领导高管、做生意的、国企事业单位、家里有田、拆二代、爷爷奶奶带大、在亲戚家长大、单亲或离异、父母有退休金）、是否吸烟/喝酒/打牌
- **隐私字段录入**：资产（房车情况、收入）、联系方式（手机号、微信）——存储但默认对他人隐藏（P3 授权解锁）
- **相册**：5 张分类照片（日常生活/兴趣爱好/旅行经历/家有萌宠/健身运动）
- **我的故事**：5 个（话题 + 语音录制上传云存储）
- **我的标签**：爱好/性格/喜欢食物/喜欢影视（预设池多选）

### 4.4 我的资料卡预览
- 现有 `recommend-card` 增强为完整资料卡组件：上侧（嘉宾编号|是否实名、头像、语音播放、个性签名）+ 下侧（昵称(性别)|情感状态、年龄、身高、星座、家乡、现居地、学校|学历、职业、是否吸烟/喝酒/打牌、恋爱目标）+ 关于我 + 希望你 + 我的标签 + 家庭背景 + 我的生活（照片）+ 我的故事（话题+语音）
- 预览页 = 他人视角的详情页雏形，语音播放、照片浏览可用

### 4.5 设置页
帮助、关于、用户协议、隐私政策（静态页，微信婚恋类目审核必需）、注销（删除账号数据，微信官方要求）、退出登录。

### 4.6 云函数
`login`、`getMyProfile`、`updateProfile`；文件用 `wx.cloud.uploadFile` 直传云存储。

**不做**：浏览他人（P2）、配额（P2）、互动（P3）、认证（P4）、DNA（P5）。

## 5. P2 — 遇见：浏览与配额

**目标**：能按条件筛选、查看嘉宾完整资料，角色配额生效。

### 5.1 遇见列表
- 「推荐」tab 更名「遇见」，完整资料卡列表（分页加载）
- 默认排序：最新注册在前（匹配度加权留到 P5）

### 5.2 筛选面板
| 维度 | 交互 |
|---|---|
| 年龄 / 身高 | 范围选择（双端） |
| 学历 / 婚姻状况 | 多选 |
| 现居地 / 职业 | 分类（省→市 / 职业类别）多选 |

筛选条件在云函数端执行（数据库查询）。

### 5.3 资料详情页
- 完整资料卡（同 4.4 的全部区块）
- 隐私字段：🔒「征求同意后可见」占位（申请流 P3 激活）
- 按钮组：心动/聊天/无感——展示但点击提示「即将开放」（P3 激活）
- 更多菜单：分享（微信转发卡片）、举报（表单写入 `reports`，P4 处理）

### 5.4 角色配额执行

| 角色 | 概览列表 | 资料详情 | 联系方式 |
|---|---|---|---|
| 游客（未登录） | ✅ | ❌ 点详情→登录引导 | ❌ |
| 普通用户 | ✅ | 5 个/天 | ❌（需授权，P3） |
| 认证用户 | ✅ | 15 个/天 | ❌（需授权，P3） |
| 管理员 | ✅ | 不限 | ✅ 直接可见（不经授权流） |

- 新增 `config` 集合存配额数字（P4 前在云开发控制台修改）
- 新增 `view_logs` 集合记录当日查看数（P3 复用为「谁看过我」）

### 5.5 云函数
`listProfiles`（筛选+分页）、`getProfileDetail`（配额校验 + 记录查看 + 按角色裁剪隐私字段）。

**不做**：心动/授权写库（P3）、认证提交（P4）。

## 6. P3 — 互动与隐私授权

**目标**：心动互配闭环 + 征求同意解锁联系方式，导流微信聊天。

### 6.1 心动 / 无感
- 新增 `interactions` 集合：`{ fromUser, toProfile, type: 'like' | 'pass', createdAt }`
- 心动：详情页按钮组写库；互相心动 → 匹配成功，双方收到系统通知
- 无感：记录后遇见列表不再出现该嘉宾

### 6.2 谁看过我 / 喜欢我的
- 谁看过我：复用 `view_logs`，倒序列表
- 喜欢我的：`interactions` 中指向我的心动列表

### 6.3 消息 tab — 系统通知流
- 新增 `notifications` 集合：心动、被查看、匹配成功、授权请求/结果
- 消息页从 mock 会话改为真实通知列表（未读红点、已读标记）
- 匹配成功通知引导发起「联系方式授权」，交换后去微信聊天（不自建 IM）

### 6.4 隐私字段授权流（本阶段核心）
```
申请方：详情页点「查看联系方式/资产」
   → consents 集合创建请求 {requester, owner, field: contact|asset, status: pending}
   → 对方消息 tab 收到请求 → 同意 / 拒绝
   → 同意后申请方解锁对应字段；owner 可随时撤销，字段重新隐藏
```
- 管理员不受此流程限制（P2 已定直看）

### 6.5 分享与举报
- 分享转发卡片带嘉宾编号 → 落地详情页（走游客配额逻辑）
- 举报表单（类型+描述+可选截图）→ `reports` 集合

### 6.6 云函数
`interact`、`getInteractions`、`requestConsent`、`respondConsent`、`getNotifications`、`markRead`、`report`。

### 6.7 P2 终审遗留（P3 立项时并入，2026-08-19）

- **配额原子化**：getProfileDetail 读 view_logs → 比较 → 写入非原子，并发首看可超额 +1。TCB 事务不支持 where 查询——改 viewer+dateKey 计数器文档 `inc` 后回读校验，或 view_logs 唯一索引+写后复核；与「谁看过我」的 `view_logs(viewerOpenid+dateKey)` 复合索引一并规划。
- **getProfileDetail 补 basicInit 防御**：未完善资料不上列表但可被直链/分享看详情（`if (!target.basicInit) return { error: 'not found' }`）。
- **详情页错误区分**：云调用 null（网络/未部署）现按 notFound 兜底显示「嘉宾不存在或已下架」——应区分「加载失败请重试」+重试按钮。
- **onLoginRetry 空转**：本地缓存与服务端档不一致时重试无反馈；重试仍 login required 时 `clearLogin()` 强刷一次。
- **E2E 断言增强**：p2-meet it1 空列表平凡通过（补断言 `loadError === false` 或播种第二账号）；it3 `privacy` toTruthy 对 `{}` 平凡通过（断言具体字段）。
- 小项：filter-panel 组件内全局工具类样式隔离治理；年龄/身高 min>max 前端钳制；mock-db 保真度（同型比较/多字段排序，按需）；`profiles.createdAt` 缺失时从 `users.createdAt` 回填。

## 7. P4 — 认证与管理能力

**目标**：人工认证体系 + 小程序内管理页，产品可运营。

### 7.1 我的认证（用户侧）
- 身份 / 学历 / 职业三类认证，各自提交材料（图片上传云存储）
- 新增 `verifications` 集合：`{ userId, type, materialFileIDs, status: pending/approved/rejected, reviewedBy }`
- 审核通过后 `users.role` 升级为认证用户（配额 5→15 自动生效）

### 7.2 小程序内管理页（管理员侧，登录后按 role 解锁）
| 功能 | 说明 |
|---|---|
| 认证审核 | 查看材料 → 通过/驳回 |
| 配额配置 | 修改 `config` 中普通/认证用户每日查看数 |
| 嘉宾管理 | 上下架（=「我要上墙」：小程序/公众号两个渠道开关）、强制资料隐藏 |
| 举报处理 | `reports` 列表 → 处理标记（下架/忽略） |

### 7.3 运营功能
- 推荐给好友：标准小程序分享
- 加入交友群：群二维码页，仅认证用户可见

## 8. P5 — 匹配增强（降级版）

**目标**：差异化匹配体验，全部基于已有标签/问卷数据，不自建音视频。

### 8.1 恋爱 DNA
- 问卷模块：趣味测试 + 人格测试（初级/进阶/深层三级灵魂测试）
- 结果存入 `profiles.dna`，详情页展示 DNA 概要与双方匹配度
- 他人 DNA 详情走 P3 授权流（复用 `consents`）

### 8.2 三种匹配方式
- 标签匹配：个人标签重合度打分排序
- 话题匹配：话题下拉筛选 → 筛出有该话题故事的嘉宾 → 一对一引导（交换联系方式流）
- 故事匹配：故事类型下拉筛选

### 8.3 遇见列表加权
默认排序改为：匹配度（标签重合 + DNA 匹配）加权 + 最新注册兜底。

### 8.4 可选项（最后做，取决于合规评估）
附近的人：位置授权 + 距离展示。企业主体能力可行，但需单独评估婚恋类目下位置权限的审核风险，评估不通过则不做。

## 9. 贯穿性设计

### 9.1 数据模型演进
| 阶段 | 新增集合/字段 |
|---|---|
| P1 | `users`、`profiles` |
| P2 | `config`、`view_logs` |
| P3 | `interactions`、`consents`、`notifications`、`reports` |
| P4 | `verifications` |
| P5 | `profiles.dna` 字段、`config` 内问卷题库 |

### 9.2 技术架构（沿用骨架）
- 微信云开发：云函数（Node.js）+ 云数据库 + 云存储；`utils/request.js` 封装沿用
- 组件化：资料卡组件（P1 建，P2 复用为列表卡/详情卡）、筛选面板、通知项
- 主题色 `#FF5A5F` 沿用

### 9.3 测试策略（沿用三层，每阶段）
- 单元：utils（星座推算、配额计算、匹配度打分）、组件（资料卡字段渲染）
- 集成：每个云函数 mock 云数据库
- E2E：每阶段关键路径（P1 登录+编辑+预览、P2 筛选+配额、P3 心动+授权流、P4 认证审核、P5 问卷+加权排序），使用 `e2e-test` skill

### 9.4 合规要点
- P1 必须上线用户协议 + 隐私政策（婚恋类目审核必需）
- 隐私字段默认隐藏 + 授权流 + 可撤销（P3）
- 注销能力（P1 设置页，微信官方要求）
- 附近的人单独做合规评估（P5 可选项）

## 10. 各阶段验收口径

| 阶段 | 验收标准 |
|---|---|
| P1 | 新用户可登录、完整编辑资料（含相册/故事/标签/隐私字段）、预览自己的完整资料卡；单测+集成+E2E 通过 |
| P2 | 遇见列表可筛选分页；游客/普通/认证/管理员四种角色的查看权限与配额行为符合 5.4 表格；E2E 覆盖配额边界 |
| P3 | 心动互配触发通知；授权流全链路（申请→同意→解锁→撤销）可用；举报可提交 |
| P4 | 认证提交→审核→角色升级→配额变化全链路可用；管理页四项功能可用 |
| P5 | 三级问卷可完成并写入 DNA；列表按匹配度加权排序；话题/故事筛选可用 |
